## 1. 배경 및 문제 정의

화주는 화물을 운송해줄 기사를 구할 때 보통 카톡이나 전화로 요청을 주고받는다. 이 비정형 텍스트를 화주가 직접 항목별로 정리해서 등록하는 과정, 그리고 "이 운임이 적정한지" 감을 잡기 어려운 문제가 있다.

화주 페이지는 이 두 마찰을 없애는 것이 핵심 가치다:
1. **문장을 그대로 붙여넣으면 AI가 항목별로 정리한다** (수기 입력 제거)
2. **등록 직후 구간 시세와 비교해 운임이 적정한지 바로 알려준다** (운임 눈치싸움 제거)

## 2. 목표

- 화주가 자연어 요청 한 줄을 붙여넣는 것만으로 화물 등록까지 3단계 내에 끝낸다.
- 화주가 운임을 "감"이 아니라 실제 구간 시세 데이터를 근거로 정한다.
- 등록 후 기사가 수락하면 배차 정보(연락처 포함)를 화주가 바로 확인한다.

## 3. 사용자 흐름 (mockup 기준)

mockup은 3개 카드(01→02→03)를 한 화면에 세로로 배치했지만, 실제로는 아래 3단계가 순차적으로 진행되는 플로우다.

```
[01 화물 요청 입력] --AI 자동 변환--> [02 AI 변환 결과 + 운임 코칭] --등록--> [03 매칭 기사 확인]
                                              ↑ 수정하기 / 재매칭 (루프백)
```

- **화주가 "수정하기"를 누르면** 02번 카드가 편집 가능한 폼으로 바뀌고, 저장 시 값이 바뀐 항목만 반영된다.
- **화주가 "재매칭"을 누르면** 같은 원문을 AI가 다시 파싱하거나(문구를 고쳐 재시도), 조건은 그대로 두고 시세만 다시 조회하는 것으로 해석될 수 있다 — §8 오픈 이슈 참고.
- 03번 카드는 아직 기사가 수락하지 않았다면 노출되지 않아야 한다(등록 직후에는 "매칭 대기 중" 상태 표시가 필요 — mockup에는 없는 상태다, §7 참고).

## 4. 기능 요구사항

### F-1. 화물 요청 자연어 입력 🤖 **[AI 필요]**

- 화주가 카톡·전화로 받은 문장을 그대로 붙여넣는 자유 텍스트 입력창을 제공한다.
  - Placeholder 예시: *"내일 서울→부산 냉장 5톤 예산 50만원"*
- "AI 자동 변환" 버튼을 누르면 아래 F-2로 넘어간다.
- **AI가 필요한 이유**: 출발지·도착지·화물종류·중량·희망운임·상차/하차 일시라는 6개 항목을 비정형 문장에서 뽑아내야 한다. 정규식/키워드 매칭으로는 "내일"같은 상대 날짜 표현이나 자유로운 어순을 감당할 수 없다.
- **입력 검증**: 빈 문장 제출은 막는다. 문장 길이 상한(예: 500자)을 둔다.

### F-2. AI 변환 결과 확인 및 수정 🤖 **[AI 필요 — 파싱 결과 표시]**

- F-1의 AI 파싱 결과를 다음 형태로 보여준다:
  - 구간 (출발 → 도착), 운임(강조 표시)
  - 데이터 그리드: 화물종류 · 중량 · 상차일시 · 하차일시
- **읽지 못한 항목은 빈 값/placeholder로 표시**하고 화주가 직접 채우게 한다 (AI가 모든 것을 알아내지 못할 수 있다는 전제).
- 버튼 2개:
  - **재매칭**: 값을 그대로 두고 다시 조건을 확인한다 (재파싱 또는 재조회, §8에서 확정 필요)
  - **수정하기**: 각 항목을 인라인으로 고칠 수 있는 편집 모드로 전환한다
- **출발지·도착지를 AI가 못 읽었을 경우** 등록을 막고 사용자에게 직접 입력을 요구한다(파싱 실패 처리). 그 외 항목은 null 허용.

### F-3. 운임 코칭 배너 🤖 **[AI 필요]**

- F-2의 운임과 **같은 구간·화물 조건의 평균 시세**를 비교해 경고 배너를 띄운다.
  - mockup 문구: *"입력하신 운임이 이 구간 평균(72만원)보다 30% 낮아요. 확인해보세요"*
- **동작 조건**: 희망운임이 해당 구간 "당일 매칭 임계 운임" 미만일 때만 경고를 노출한다. 임계 이상이면 배너 없이 바로 진행 가능해야 한다(적정 운임일 때 굳이 경고를 띄우지 않음).
- **AI가 필요한 이유**: 화물 매칭 플랫폼에 자체 축적된 실거래 운임 데이터가 없는 해커톤 특성상, 구간·화물조건별 평균 시세 자체를 AI가 추정한다. 같은 조건이면 항상 같은 값이 나와야 하므로 **1차 조회 후 DB에 캐싱**해서 재현성을 확보한다 (매 호출마다 AI에게 새로 묻지 않음).
- 화주가 배너를 보고 "수정하기"로 운임을 올리면, 값이 바뀐 시점에 시세를 다시 비교해 배너가 사라지거나 갱신되어야 한다.

### F-4. 화물 등록

- F-2에서 확인/수정을 마친 최종 값을 저장한다. 등록 직후 상태는 "매칭 대기중"이다.
- AI 관여 없음 — 단순 저장.

### F-5. 매칭 기사 확인 및 연락

- 기사가 수락하면 배차된 기사 카드를 보여준다:
  - 기사명 · 차량 (예: "김OO 기사 · 냉장탑차 5톤"), 운임 적정성 배지("적정 운임")
  - 상세 정보: 차량번호, 운행지역, 평점(건수 포함), 완료율, 최근 운행 이력, 연락 가능 시간, 희망 최소 단가, 선호 도착지역
  - "전화하기" 버튼으로 기사에게 즉시 연결
- **AI 관여 없음** — 이 화면에 뜨는 "적정 운임" 배지는 F-3에서 이미 계산된 시세 판정 결과를 재사용하는 것이고, **화물↔기사 매칭 자체는 규칙 기반 스코어링**(구간일치 + 차량적합 + 시간여유 + 운임매력 가중합)으로 동작한다. AI 호출 없이 응답 속도를 확보하고, "왜 이 기사가 배정됐는지"를 규칙으로 설명 가능하게 하려는 의도적 설계다.
- 화주는 배차 여부를 폴링으로 확인한다(실시간 푸시 없음 — 화면의 "다시 찾기"류 재조회 버튼이 곧 폴링 트리거).

## 5. AI 필요 기능 요약

| 기능 | AI 사용처 | AI 없이 대체 불가능한 이유 | 실패 시 폴백 |
|---|---|---|---|
| 🤖 F-1/F-2 자연어 파싱 | 문장 → 구조화된 화물 항목 6종 추출, 상대 날짜("내일") 절대시각 변환 | 규칙/정규식으로는 자유 어순·구어체 문장을 감당 못 함 | 출발/도착 미인식 시 422 에러로 수동 입력 유도. 나머지 항목은 null 허용 후 화주가 채움 |
| 🤖 F-3 구간 시세 추정 + 운임 코칭 | 구간·화물조건별 평균 운임 및 "당일 매칭 임계 운임" 추정 | 실거래 데이터 없이 시세 감을 제공할 유일한 방법 | AI 호출 실패 시 배너 없이 등록 흐름은 그대로 유지 (운임 코칭은 부가 기능이지 등록을 막는 필수 관문이 아니어야 함) |

**AI가 아닌데 AI처럼 보이는 부분** (오해 방지용): F-5의 매칭 기사 선정과 "적정 운임" 배지는 룰 기반 계산 결과다. 발표/데모 시 AI 활용 포인트를 설명할 때 이 둘을 섞어 말하지 않도록 주의.

## 6. 화면 밖 범위 (Out of scope)

- 회원가입·로그인 (화주는 이미 가입되어 있다고 가정, `X-User-Id` 헤더로 식별)
- 화주의 과거 등록 이력 목록/재사용
- 배차 후 실시간 위치 추적, 정산
- 실시간 푸시 알림 (폴링으로 대체)
- 화물 등록 취소 이후 재등록 플로우 (mockup에 없음)

## 7. Mockup에 없지만 필요한 상태 (구현 시 보강 필요)

- **매칭 대기 중** 상태 UI: F-4 등록 직후 ~ 기사 수락 전까지 03번 카드 자리에 무엇을 보여줄지 mockup에 정의되어 있지 않다. "기사를 찾고 있어요" 류의 대기 화면이 필요하다.
- **파싱 실패 상태 UI**: F-1에서 AI가 출발/도착을 못 읽었을 때의 에러 표시가 mockup에 없다.
- **로딩 상태**: "AI 자동 변환" 버튼 클릭 후 응답 대기 중 스피너/스켈레톤 (Opus 계열은 파싱에 수 초 걸릴 수 있음).

## 8. 오픈 이슈

1. **"재매칭" 버튼의 정확한 동작 정의 필요** — (a) 같은 원문을 AI에게 다시 파싱시키는 것인지, (b) 조건은 유지한 채 시세만 재조회하는 것인지 mockup 문구만으로는 모호하다. 화면 흐름상 F-3 운임 코칭 갱신 트리거일 가능성이 높다.
2. **운임을 낮게 등록해도 강행할 수 있는가** — F-3 경고는 "확인해보세요"라는 소프트 워닝이다. 경고를 무시하고 그대로 등록을 진행할 수 있어야 하는지(현재 설계는 가능) 재확인 필요.
3. **AI 파싱/시세 응답 지연에 대한 데모 안전판** — 두 기능 모두 Claude API 장애 시에도 화주의 "직접 입력 후 등록"까지는 막히지 않아야 한다 (F-3는 배너만 생략, F-1은 수동 입력 폼으로 폴백).
